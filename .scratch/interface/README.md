# Интерфейс iPhone — с чего начать

Ты берёшь один тикет из `issues/` и доводишь его до конца. Этот файл — всё, что
нужно знать до первой строчки кода.

## Прочитай в этом порядке

1. **`/CLAUDE.md`** — правила репозитория. Четыре шва, `Views/` только macOS,
   относительные пути, где живут тесты. Нарушение этих правил — дефект, даже
   если код работает.
2. **`docs/superpowers/specs/2026-08-05-petrichor-ios-design.md`**, разделы
   «Интерфейс» и «Порядок сборки» — канон дизайна. Он утверждён. Если код с ним
   расходится, чинится код, а не спека.
3. **`docs/research/2026-08-05-ios-26-interface-apis.md`** — какие API iOS 26
   доступны, проверено по SDK. Там же перечислено, что именно в текущем
   `iOS/ContentView.swift` противоречит спеке, с номерами строк.
4. **`spec.md`** рядом с этим файлом — решения, принятые до тикетов.
5. Свой тикет.

## Как собрать и проверить

```bash
xcodebuild -scheme PetrichoriOS -destination 'platform=iOS Simulator,name=iPhone 17 Pro Max' build
xcodebuild test -scheme PetrichoriOS -destination 'platform=iOS Simulator,name=iPhone 17 Pro Max'
```

Мак тоже должен собираться — общие слои входят в оба таргета:

```bash
xcodebuild -scheme Petrichor -destination 'platform=macOS' build
```

На реальный телефон:

```bash
.claude/skills/petrichor-device/scripts/deploy.sh
```

Обычный device destination на этой машине **не работает** — Xcode 26.6 против
iOS 27 beta на устройстве. Не чини его, читай `.claude/skills/petrichor-device/SKILL.md`.

## Как выбрать тикет

**Все тикеты 01–10 закрыты (`Status: done`).** Интерфейсный слой реализован и
смержен в `ios-port` (интеграция — коммит `8b23bf7`), приёмка на устройстве
пройдена через `library-parity/04-device-acceptance`. Открытого фронтира здесь
нет — новые задачи по интерфейсу заводятся отдельными тикетами (следующий
крупный блок — дизайн-проход «как Apple Music», начинается с обновления спеки).

Примечание по 02: zoom-переход от обложки позже заменён на in-hierarchy оверлей
ради отзывчивости мини-плеера (коммит `801ff25`) — тикет остаётся `done`,
изменение подхода зафиксировано в истории.

Если берёшь новый тикет: `Status: in-progress` до начала, `Status: done` и
галочки по факту в конце. Незакрытый критерий оставь незакрытым с причиной —
недоделанная галочка честнее проставленной. Один тикет за раз, чистый контекст
между тикетами.

## Грабли, на которые наступают чаще всего

- **Мини-плеер нельзя оборачивать в `if`.** `tabViewBottomAccessory` внутри
  условия роняет приложение в паре с `TabView(selection:)`. Видимость задаётся
  перегрузкой `tabViewBottomAccessory(isEnabled:content:)`.
- **Не адаптируй макошные вьюхи.** `Views/` остаются macOS-only, iOS-экраны
  пишутся заново в `iOS/`. Ветки `#if os(iOS)` внутри `Views/` — наследие,
  которое каждый тикет забирает с собой, а не образец.
- **Не пиши свой плавающий плеер.** Спека прямо запрещает: мини-плеер системный.
- **Пути в базу пишутся относительно `Documents/`.** Код, кодирующий `url.path`
  напрямую, ломает переустановку приложения.
- **Тесты только на четырёх швах.** SwiftUI-вьюхи тестами не покрываются, их
  проверка — симулятор и устройство.

## Что считается сделанным

- Критерии тикета выполнены или явно помечены как невыполненные с причиной.
- Обе платформы собираются, тесты зелёные.
- Изменения закоммичены. Ветка `ios-port`, `main` не трогаем.
- Если тикет требует проверки на устройстве — она проведена на устройстве, а не
  в симуляторе. Симулятор не отвечает на вопросы про фон, блокировочный экран и
  поведение бета-API.
